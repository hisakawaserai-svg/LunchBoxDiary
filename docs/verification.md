## 1. 写真の縮小(サムネイル)

### 背景(なぜこの実験をしたか)
- このアプリは写真が主役。カレンダーには1か月分(前後を含めると約90マス)、リストには数百件の写真が並ぶ
- 元画像は1枚4MB前後(実測 4,127,524 バイト)。画面に出すときは展開されて、おおよそ「画素数 × 4バイト」のメモリを使う(1200万画素なら約48MB)
- 小さなマスに出すだけなのに、毎回4MBの元画像を読んで展開するのは重そうだと考えた
- そこで、2つの方法を比べることにした

| 方法 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A 表示のたびに縮小 | 保存するのは元画像だけ。マスに出すたびに縮める | 保存データが増えない | 毎回、元画像を読んで展開する |
| B 保存時に縮小版も作る | 保存するときに縮小版も作って保存する。マスには縮小版を出す | 表示のときは小さい画像を読むだけ | 保存データが増える。保存時の処理が増える |

- Bの「保存データが増える」が許せる大きさか、実際に測って確かめることにした

### 目的
Bを採用してよいか判断するために、縮小版の大きさ(バイト数)と画素数を測る。

### 仮説
- 保存時に縮小版(360px 四方に収まる大きさ)を作れば、1枚あたり数十KBに収まる
- 元画像は4MB前後のため、縮小せずに並べると重くなる

### 方法
`PhotosPicker` で選んだ画像を `UIImage` にして、`preparingThumbnail(of:)` で縮小した。

```swift
.task(id: selectedImage){
    guard let selectedImage else { return }
    guard let data = try? await selectedImage.loadTransferable(type: Data.self) else { return }
    print("元画像のバイト数: \(data.count)")
    image = UIImage(data: data)
}
.task(id: image) {
    guard let image else { return }
    guard let thumb = image.preparingThumbnail(of: CGSize(width: 360, height: 360)) else { return }
    thumbnail = thumb
    print("CGWidth: \(thumbnail?.cgImage?.width) CGHeight: \(thumbnail?.cgImage?.height)")
    print("サムネイルの圧縮後のバイト: \(thumbnail?.jpegData(compressionQuality: 0.8)?.count ?? 0)")
}
```

### 結果

| 元画像(バイト) | サムネイル(px) | JPEG 0.8 後(バイト) |
|---|---|---|
| 4,127,524 | 360 × 270 | 60,750 |
| 993,045 | 240 × 360 | 29,490 |

- 縮小版は最大でも約61KB
- 年間の容量の見積り(1日1件、元画像を縮小せずに残す場合): (61 + 4000)KB × 365 = 1,482,265KB ≒ 約1.5GB
  - 内訳: 縮小版 61KB × 365 ≒ 22MB(約1.5%)、元画像 4000KB × 365 ≒ 1.46GB(約98.5%)
  - 容量のほとんどは、縮小版ではなく元画像。縮小版を増やしても減らしても、ほぼ変わらない
- 見た目: 少し粗いが、カレンダーのマスやリストで困らない程度
- 詳しいログと途中経過は Notion の「写真の縮小を実測で決めた話」に残してある

### 判断と理由
- 判断: 保存時にサムネイルも作って保存する。縮小には `UIImage.preparingThumbnail(of:)` を使う。大きさは 360px 四方に収まる大きさ(大きさと保存の内容は、のちに 1-2 で更新した)
- 理由: 圧縮すれば大した容量にならない(縮小版は最大でも約61KB)のと、毎回計算し直すことが負担になっていると判断した
  - 注: 「毎回計算し直すのが負担」は、まだ測っていない仮説。画像表示の処理能力のテスト(3章)で確かめる

### 残っていること
- [ ] 縦向きの写真で向きが正しいか(サムネイルの `size` と `imageOrientation`、保存して読み戻した画像)
- [x] 元画像をそのまま残すか → 1-2 で決定(元画像は保存しない)
- [x] JPEGの品質 → `0.8` は、よく使われている値として仮置きしたもの。1-2 で品質を変えて比べ、0.5 に決定

### 1-2. 追加実験: 圧縮と縮小のどちらが効くか、JPEG品質はいくつか

#### 目的
容量(約1.5GB/年)を減らす方法を決める。圧縮と縮小のどちらが効くか、JPEG品質をいくつにするか、元画像を残すかを決める。

#### 仮説
- 縮小の効果は、圧縮よりずっと大きい
- 画像のデータ量はおおよそ「幅 × 高さ」に比例する。4000×3000px を 360×360px にすると、画素数は約1/92になる(Claude Code の説明をもとに、画素数を計算した)

#### 方法
同じ写真について、次の4つのバイト数を表示した。
- 元画像
- 圧縮のみ(縮小しないで、JPEG品質 0.8 にする)
- 縮小のみ
- 縮小 + 圧縮(JPEG品質 0.8)

さらに、メイン(拡大表示用)とサムネイルの2つを、JPEG品質を変えて保存した場合のバイト数を比べた。保存の仕組みは作らず、バイト数を表示するだけにした。

「縮小のみ」は、サムネイル(200px)をJPEG品質 1.0 で保存したバイト数として測った(縮小だけを測るため、圧縮を最小にした)。

```swift
.task(id: "\(selectedImage?.itemIdentifier ?? "")-\(compression)") {
    guard let selectedImage else { return }
    guard let data = try? await selectedImage.loadTransferable(type: Data.self) else { return }
    image = UIImage(data: data)

    print("----------------")
    print("元画像: \(data.count)B | 圧縮率: \(compression)")
}
.task(id: image) {
    guard let image else { return }

    guard let detail = image.preparingThumbnail(of: CGSize(width: detailPx(), height: detailPx())) else { return }
    guard let detailCompression = detail.jpegData(compressionQuality: compression) else { return }
    detailImage = UIImage(data: detailCompression)

    guard let thumb = image.preparingThumbnail(of: CGSize(width: 200, height: 200)) else { return }
    guard let thumbCompression = thumb.jpegData(compressionQuality: compression) else { return }
    thumbnailImage = UIImage(data: thumbCompression)

    print("サムネ縮小のみ: \(thumb.jpegData(compressionQuality: 1.0)?.count)B")
    print("メイン画像: \(detailCompression.count)B | サムネ画像: \(thumbCompression.count)B")
    // 以降は省略
```

メインは `detailPx()`(画面の幅 × スケール)に収まる大きさ、サムネイルは 200px に収まる大きさで縮小し、同じ品質(`compression`)でJPEGにして、バイト数を表示した。

`detailPx()` の中身(実験で使ったもの):

```swift
func detailPx() -> CGFloat {
    let scale = UIScreen.main.scale
    let width = UIScreen.main.bounds.width
    return width * scale
}
```

- `UIScreen.main.scale`: 画面の倍率(1ptが何pxか。たとえば 3)
- `UIScreen.main.bounds.width`: 画面の幅(pt。たとえば 393)
- 幅 × 倍率 = 画面の幅のpx数(たとえば 393 × 3 = 1179)。これを、メイン画像の「収める四角」の一辺に使う
- 確認: Xcode でエラーは出なかった。`UIScreen.main` は、iOS 16 以降で、使わないよう勧められている(非推奨)とされる。警告は出なかった(本人の確認)
- 注意: `bounds.width` は、画面を横向きにすると、縦の長さになる。写真の大きさが端末の向きで変わらないか、確認する(横向きになる可能性はある。向きで値が変わるかは、未検証)

`.task(id:)` の id は、品質を変えて何度も走らせるために、実験中だけ `itemIdentifier` と `compression` をつないだ文字列にした。実験のあとは `selectedImage` に戻した。

#### 結果

圧縮と縮小の比較(JPEG品質 0.8):

| | 元画像(バイト) | 圧縮のみ | 縮小のみ | 縮小 + 圧縮 |
|---|---|---|---|---|
| 写真1 | 3,338,583 | 3,318,766(元の99.4%) | 171,384(5.1%) | 48,910(1.5%) |
| 写真2 | 2,823,679 | 2,807,464(元の99.4%) | 159,495(5.6%) | 43,847(1.5%) |

- 圧縮だけでは、元画像から0.6%しか減らなかった
- 縮小すると約1/20、縮小して圧縮すると約1/65〜1/68になった
- 仮説の「画素数は約1/92」ほどは減らなかった。縮小の効果が圧縮よりずっと大きい、という大筋は合っていた
- 上の表の「縮小のみ」(171,384 など)が、方法に書いた測り方(JPEG品質 1.0)と同じか、縮小後の大きさが何pxだったかは、記録が残っていない【確認】
- 方法に書いた実験では、元画像(3,338,583B)から、サムネイル(200px、品質 1.0)は 59,308B になった。縮小だけで元の約1.8%

- 保存するもの: メイン(拡大表示用)とサムネイル(カレンダーのマスやリスト用)の2種類

## 2. カレンダーの日付と月の作り方

### 目的
月のマスを作るために、月の最終日と、日付の扱い方を決める。

### 起きたこと
翌月の0日(`day: 0`)で月の最終日を求めたところ、`11月29日` と出た。

```swift
let lastDayDate = DateComponents(year: nextYearValue, month: nextMonthValue, day: 0)
let lastDay = calendar.date(from: lastDayDate)
print("\(String(describing: lastDay))")
```

```
Optional(2026-11-29 15:00:00 +0000)
```

`Date` を `print` すると UTC で表示される。15:00 UTC は日本時間で 11月30日の0時。`calendar.component` で一つずつ見ると 2026 / 11 / 30 / 0 で正しかった。

### 判断と理由
- 日付は日本時間の0時ちょうど(`startOfDay`)にそろえる。マスの日付も、記録の日付も同じ形にして、同じ日かどうかを `==` で比べられるようにする
- 画面に出す日付は `calendar.component` で取り出す(`print` した `Date` は UTC 表示のため)
- 月の窓: 前月・今月・来月の3か月分だけ作る。月を移動するときは、片側に1か月足して、反対側を1か月捨てる(`getMonthGroups`)。今見ている月が、常に真ん中になる
- 月初の空きマス: `MonthGroup.dates` を `[Date?]` にして、空きマスは `nil` にする。数は、月初の `weekday - 1`(日曜始まり)
- 【自分で書く】なぜ3か月だけ作るのか、なぜ空きマスを `nil` にしたのか

### 残っていること
- [ ] 週の始まりを日曜に固定してよいか(`calendar.firstWeekday` を使うか)
- [ ] 曜日の見出し

## 7. 色の変換(`Color` と 16進数の文字列)

### 目的
- `ColorPicker` の `Color` を、SwiftData に保存できる形(文字列)にし、表示のときに `Color` に戻す

### 起きたこと(実行結果)
- 最初の `colorToStr`: `String(Int, radix: 16)` で作った。1桁の値(0〜15)が、桁そろえされない
- 次に、`String(format: "%02X", ...)` に、文字列を渡した → 黒で `EDE6912A EDE6912A EDE6912A` のような、意味のない値になった(数値用の書式に、文字列を渡したため)
- 次に、小数(`Float`)のまま渡した → 黒で `00 00 00` と出て、合って見えた。0 は、小数でも整数でも内部の表し方が同じため、偶然合っていただけで、黒では、バグが見つからなかった
- 整数に直して(`Int(... .rounded())`)、白で `FF FF FF` を確認した
- `Color(red: 10/255, green: 161/255, blue: 15/255)` で、`resolved` の表示が `#0AA10FFF`(赤 0A、緑 A1、青 0F、不透明度 FF)になり、1桁の値が含まれることを確認した
- `resolve(in:)` は、Xcode の Quick Help で、iOS 17 以上の API と確認した

### 判断と理由
- 保存は文字列、表示は `Color`。理由: SwiftData に `Color` を保存できないため
- `%02X` で、桁そろえと16進数への変換を一度に行う(桁そろえのための処理を、別に書かない)
- テストの色は、黒だけでなく、0 以外の値や、1桁の値を含む色を使う(黒は、バグが隠れやすい)

### 残っていること
- [ ] `colorToStr` の戻り値を、`Color(hex:)` で戻して、元の色と同じか(往復)の確認

- `Frame`(`struct`。テーマの `enum` と、色の文字列)を、`LunchBox` に持たせて保存し、読み戻して、`FrameView` で表示できるか確かめる(設計の前提)

### 方法
- `FrameView` に、タイトル、写真、フレームのテーマと色だけを渡す簡易な形で試した
- 保存した記録(テーマ `.def`、色 `.black` = `#000000`)を読み出して、表示した
- アプリを強制終了して開き直し、前日に作ったデータが表示されることを確認した。アプリを削除して入れ直すと、データは消える(仕様どおり)

### 結果(確認)
- 保存した `.def` と黒が、読み戻せた。カード、星、写真の窓、日付とタイトルが、表示された
- 背景が黒のため、文字は、`textColor` の働きで、白になった

### 判断と理由
- `Frame` を `struct`(`Codable`)として `LunchBox` に持たせる形で進める(設計書の2章のとおり)
